# Expirations are read-only via the API: no `POST /expirations` exists (and the route returns HTML)

**Endpoints:** `POST /api/v1/expirations` (absent), `GET /api/v1/expirations`, `PUT`/`DELETE /api/v1/expirations/{id}`

## Exact requests and observed responses

```bash
curl -sS -X POST "$HUDU_BASE_URL/api/v1/expirations" -H "x-api-key: $HUDU_API_KEY" \
  -H 'content-type: application/json' -d '{}'
```
```
HTTP 404
<!DOCTYPE html><title>404</title>...    (HTML error page, not the API's JSON error envelope)
```

```bash
curl -sS -X POST "$HUDU_BASE_URL/api/v1/expirations" -H "x-api-key: $HUDU_API_KEY" \
  -H 'content-type: application/json' \
  -d '{"expiration":{"date":"2027-01-01","expirationable_type":"Website","expirationable_id":1,"company_id":3}}'
```
```
HTTP 404   (same HTML page)
```

`GET /api/v1/expirations?page_size=3` → `200` with pre-existing rows
(`{"id":1,"date":"2026-11-02","expiration_type":"ssl_certificate","expirationable_type":"Website",...}`).

## What the spec says instead

The vendored spec contains exactly two expiration paths, and neither creates:

* `GET /expirations` (`get_expirations`) — filters `page`, `company_id`, `expiration_type`, `resource_id`,
  `resource_type`, `archived`, `page_size`; responses `200` (array of `definitions.Expiration`), `401`, `404`.
* `PUT /expirations/{id}` and `DELETE /expirations/{id}` — `200`/`204`, `404 "Expiration not found"`, `422`.

There is no `POST /expirations`; there is also no `GET /expirations/{id}`. `definitions.Expiration`
(`expirationable_type`/`_id`, `expiration_type`, `asset_layout_field_id`, `asset_field_id`) suggests rows
are generated by other records.

## Why it matters

The write half of the resource (`update`, `delete`) is effectively untestable and unusable for a new
tenant: a client cannot create a fixture row, so those two operations can only be exercised against
pre-existing tenant data — which a test or a sandbox integration must not touch.

## Requested fix

State explicitly in the docs that expirations are read-only through the API and are produced by
website/domain/SSL sync and asset-layout expiration fields (and, if a create endpoint is planned,
document it). Minor, in the same area: a 404 for a missing route returns an HTML page instead of the JSON
error shape the rest of the API uses, which a client cannot parse.
