## Findings (ranked by severity)

- **CRITICAL** — `exports.create` and `s3_exports.create` dry-run results claim `reversible: true` for a mutation that has NO way to be undone — `src/resources/exports.ts:171`, `src/resources/s3_exports.ts:44`. Neither resource exposes a delete/cancel endpoint (`grep -n "async delete" src/resources/exports.ts` and the file itself: "the vendor exposes no list, get or delete endpoint" for s3_exports). An agent that reads `impact.reversible === true` from the dry-run result before deciding whether a risky async export job is safe to fire is told exactly the opposite of the truth. This is precisely the "SDK claims a safety property it does not have" failure mode this review was asked to find. No test in `test/resources/exports.test.ts` / `s3_exports.test.ts` asserts against this value, so nothing catches it (both files pass `npx vitest run` unchanged). Fix: set `reversible: false` for both, and drop the field's default-true framing wherever there's no compensating undo endpoint.

- **HIGH** — Bulk-delete dry-run results hardcode `affected: 1` for operations whose true affected count is an unbounded, server-computed set — `src/resources/activity_logs.ts:125` (`deleteAll`, "every activity log from `datetime` on") and `src/resources/magic_dash.ts:115` (`delete`, "every Magic Dash item with that title in that company"). `scope: 'bulk'` is set correctly, but `affected: 1` actively understates the blast radius to any caller/agent inspecting `impact.affected` before confirming a destructive bulk call — the one field policy §7.2 designates for exactly this judgment call. Contrast with `magic_dash.updatePositions` (`src/resources/magic_dash.ts:203`), which correctly reports `affected: positions.length` (the real, caller-supplied bound) — proving the pattern is known and simply wasn't applied to the other two. Fix: report `affected` as unknown/undefined-but-flagged (or omit it with a warning) rather than a literal `1`, or at minimum do not use a number that reads as "single record."

- **HIGH** — Policy §7.2/§7.3 requires the impact statement `{ affected, scope, reversible }` in **both** the dry-run result and executed-result metadata; only the dry-run half exists. `DryRunResult.impact` (`src/types/common.ts:60`) has no counterpart on any executed return value: `createOne`/`updateOne` return the bare record, `deleteOne`/`setArchived` return `void` (`src/resources/base.ts:211-346`), and `AuditEvent` (`src/types/common.ts:94-110`, emitted at `src/http.ts:284-298`) carries `correlationId/operation/method/path/effect/dryRun/outcome/httpStatus/resourceIds/query` but no `impact` field at all. An agent cannot recover "how many records did that actually affect" from anything the SDK hands back after a real (non-dry-run) mutation — only the untrustworthy pre-flight guess (see the two findings above) exists anywhere in the type system. `grep -rn "impact" src/` outside `common.ts`/`base.ts` confirms it is dry-run-only. Fix: either attach impact metadata to executed bulk-mutation results, or drop the "and in executed-result metadata" half of the policy claim from the public docs so the SDK doesn't advertise a guarantee it does not implement.

- **LOW** — `refuseExpectedUpdatedAt`/staleness-guard logic for resources with no `updated_at` (ip_addresses, rack_storage_items, flags, labels, lists, relations, flag_types, label_types) is reimplemented as a private, near-identical function in each resource file instead of shared from `src/resources/agent-layer-helpers.ts` (`grep -rln "function refuseExpectedUpdatedAt" src/resources/` → 7 separate definitions). Not a correctness bug in the instances I read (ip_addresses.ts:104-113, rack_storage_items.ts:29,134,145,156), but the duplication is exactly the kind of copy-paste surface where one future edit silently diverges and a resource starts fabricating STALE_OBJECT or silently swallowing the guard. Fix: consolidate into `agent-layer-helpers.ts` as originally intended by the module's own doc comment on `base.ts:494-505`.

- **NIT** — `capabilities.plan.json` has an uncommitted 129-line working-tree diff (see Scope note) sitting in the same file the gate (`check-capabilities.mjs`) validates; if this reviewer had been asked to run the gate as part of "additive only" it would pick up an uncommitted, out-of-scope row and could give a false read. Coordinator should ensure the plan file is clean before any gate run is used to sign off this branch.

## VERIFIED OK

- **Dry-run never reaches transport (structural, not flag-based).** Read `src/resources/base.ts:211-346`: `createOne`/`updateOne`/`deleteOne`/`setArchived` all check `if (opts?.dryRun) { return this.buildDryRunResult(...) }` and return *before* constructing the `this.http.request(...)` call — the mutating call is never reached, not merely skipped by a flag downstream. Same pattern confirmed in the multipart paths: `photos.ts:338` (before `new FormData()` at :353), `public_photos.ts:195,237` (before FormData at :210/:253), `uploads.ts:171` (before FormData at :186). Confirmed by test: `test/resources/companies.test.ts:400-407` spies on fetch and asserts `expect(spy.calls).toHaveLength(0)` after `{ dryRun: true }`.
- **Transport-level dry-run is defense-in-depth, not the load-bearing mechanism.** `src/http.ts:245-252` has its own `if (opts.dryRun === true)` short-circuit before `fetch`, but `grep -rn "this.http.request" src/resources/*.ts` shows no resource ever passes `dryRun` into a `request()` call — the resource-level short-circuit above is what actually runs.
- **Bulk operations refuse unconfirmed (POLICY_DENIED) and declare a bound.** Verified in source (`activity_logs.ts:106-115`, `magic_dash.ts:96-108`, `magic_dash.ts:175-190`) and in the registry (`capabilities.plan.json` operations for `activity_logs.deleteAll`, `magic_dash.delete`, `magic_dash.updatePositions` all list `POLICY_DENIED` in `errors` and `requiresApproval` in `flags`).
- **DELETE rows are uniformly `destructive` + `requiresApproval`.** Checked programmatically across all 225 plan rows: every `DELETE /...` endpoint has `effect: 'destructive'` and `'requiresApproval'` in flags — zero exceptions.
- **`sensitive` on asset_passwords/password_folders reads AND writes.** Checked all plan rows for both resources: every read (GET/resolve/search/findBySlug) and write (POST/PUT/archive/unarchive) row carries `sensitive`; DELETE additionally carries `requiresApproval`.
- **No combined-property enum values.** All 225 plan rows use only `effect ∈ {read, write, destructive}` and `flags ⊆ {sensitive, idempotent, requiresApproval}` — no operation encodes two properties in one string, and no POST is ever marked `idempotent`.
- **staleCheck honesty verified on 3 resources.** `companies.update` (has `updated_at`): mismatch throws `STALE_OBJECT`/`conflict`/`retryable:false` before any PUT (`test/resources/companies.test.ts:551-565`), match sends the PUT. `ip_addresses.update` (no `updated_at`): explicitly refuses `expectedUpdatedAt` with `HuduConfigError` before any request (`ip_addresses.ts:104-113`). `rack_storage_items.update`/`.create`/`.delete` (no `updated_at`): same refusal via a local `refuseExpectedUpdatedAt` (`rack_storage_items.ts:29,134,145,156`). Generic fallback in `base.ts:507-538` (`assertNotStale`) throws `HuduConfigError` (never a fabricated `STALE_OBJECT`) when a fetched record has no version field.
- **create/delete/archive refuse `expectedUpdatedAt` (no silent ignore).** `base.ts` calls `assertNoExpectedUpdatedAt` unconditionally in `createOne`, `deleteOne`, and `setArchived` (`base.ts:213,296,326`), throwing `HuduConfigError` rather than silently accepting and dropping the option.
- **Correlation ids: one per call, reused across retries, on success and error paths.** `src/http.ts:244` generates `correlationId` once at the top of `request()`, before the internal retry loop in `execute()`; it's attached to thrown errors (`:262`) and to every audit event (`:285`), on both the success and error branches (`:253/:258/:266`).
- **Error contract fields populated; `status`/`httpStatus` alias confirmed.** `src/errors.ts:89-135`: `category`, `retryable`, `resourceIds`, `suggestedAction`, `correlationId` are constructor-populated or status-derived; `status` (deprecated) and `httpStatus` (canonical) getters both return the same `_status` (`errors.ts:124,129`); 409→`ConflictError`(`category:'conflict'`), 412→`StaleObjectError`(`category:'conflict'`) are dedicated classes (`errors.ts:210,217`), not generic errors.
- **Exactly one redactor, used consistently.** `src/logger.ts:67` `redact()` is the sole implementation; `src/http.ts:298` reuses it for audit events (test title literally: `test/core-agent-layer.test.ts:429` "redact() — the one SDK redactor"). `AuditEvent` never carries a request body (`types/common.ts:94-110`), only a redacted `query`, so credential-bearing POST/PUT bodies structurally cannot leak into an audit event regardless of redaction correctness.
- **SDK does not silently redact returned data.** `test/resources/asset_passwords.test.ts:110` (`expand:true`) returns the real `password: 's3cret-value'` value untouched; only the separate compact-projection function (policy §9, not a redactor) omits the field from summaries. `redact()` is opt-in and verified to remove the field on request (`asset_passwords.test.ts:219`, `password_folders.test.ts:104`).
- **No unbounded `Promise.all`.** `base.ts` documents and implements bounded-parallelism helpers gated by `this.concurrency` (client config, default 4) for bulk work (`base.ts:544+`); consistent with the `concurrency`-bounded description already recorded in the plan for the (out-of-scope) `operations.searchAcrossResources` row.
- **Live test run.** `npx vitest run test/resources/exports.test.ts test/resources/s3_exports.test.ts test/resources/activity_logs.test.ts test/resources/magic_dash.test.ts` → 4 files, 77 tests, all passing (does not catch the reversible/affected findings above — those are semantic, not covered by any assertion).
